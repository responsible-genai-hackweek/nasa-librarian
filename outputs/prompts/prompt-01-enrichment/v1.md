# Stage 1: LLM + earthdata-mcp Query Prompt Template

## Purpose

Transform an enriched, refined user story into a dataset search against earthdata-mcp. The LLM+MCP should:

1. **Parse the explicit specification** (six slots) and translate to search constraints
2. **Query earthdata-mcp** to find candidate datasets
3. **Validate candidates against gotchas** — surface where naive picks would fail
4. **Rank by fitness** — not just relevance
5. **Refuse when nothing fits** — if all candidates fail an axis

---

## Template: The Stage 1 Query Prompt

```markdown
# Task: Find NASA Datasets Matching This Refined User Story

## Enriched Story Context

[INSERT story markdown here: raw problem + six slots + gotchas + would/wouldn't work]

---

## Your Job

You have access to NASA's `earthdata-mcp` tools. Your task is to find datasets that fit this user's actual need — not just keyword matches.

### Instructions

#### Step 1: Parse the Specification
Extract and state the hard constraints:
- **Unit of analysis:** [e.g., 1–10 km patches]
- **Spatial resolution required:** [e.g., ≤ 30 m]
- **Time window:** [e.g., 10+ years]
- **Temporal cadence:** [e.g., annual]
- **Latency tolerance:** [e.g., weeks OK; operational < 6 hrs]
- **Variables:** [e.g., vegetation + subsidence]

#### Step 2: Search earthdata-mcp
Use `get_collections()` to search for datasets matching the variables and region.

**Search strategy:**
- Start with the most specific variable (e.g., "InSAR subsidence" before "vegetation")
- Search by spatial resolution if available (e.g., "30 m Landsat" not just "Landsat")
- Search by time span (e.g., "1980–2024" for the 10+ year window)
- Search by cadence (e.g., "daily" vs "annual")

#### Step 3: Validate Candidates Against Gotchas

For EACH candidate dataset returned by earthdata-mcp, answer:

1. **Does it fit the specification?**
   - Resolution: Is it ≤ the required resolution? (Remember: coarser is worse)
   - Time span: Does it cover the required window?
   - Cadence: Is it frequent enough? (Daily, weekly, seasonal?)
   - Latency: Is the data fresh enough? (Real-time, days, weeks?)
   - Variables: Does it measure what's needed?

2. **Which gotcha does it hit (or avoid)?**
   - **From the story's "Trap for naive picker":** Would a naive searcher pick this and regret it?
   - **From regional caveats:** Does this dataset fail in this region?
   - **From measurement artifacts:** Does this have known failure modes the user is unaware of?

3. **Confidence: High / Medium / Low**
   - High: Fits spec, avoids gotchas, explicitly mentioned in "Would Work"
   - Medium: Fits spec, might hit a gotcha
   - Low: Fits some specs but fails an axis; or mentioned in "Wouldn't Work"

#### Step 4: Rank and Refuse

**Rank candidates by fitness (not relevance):**
- Candidates that avoid all gotchas → rank high
- Candidates that fit on some axes but fail others → rank medium, note the failure
- Candidates that would let the user make a silent-wrong choice → rank low with a warning

**Refuse if appropriate:**
- If all candidates fail an axis regardless (e.g., all are too coarse for the unit of analysis), refuse that axis
- Example: "Nothing in NASA's holdings resolves individual parcels at 630 m; all soil-moisture products are ≥ 3 km"
- State what WOULD work instead (e.g., "You'd need Landsat-resolution data or field surveys")

## Notes for LLM

- **Be skeptical of relevance.** earthdata-mcp's search returns ranked by relevance (keyword match). Fitness is different.
- **Gotchas are your job.** The story's "Trap for naive picker" is not obvious from dataset metadata; you have to infer it.
- **Ground truth is in "Would Work" and "Wouldn't Work".** If the story says "SMAP won't work," and you found SMAP, explain why the story is right.
- **Refusal is OK.** If every candidate fails on resolution, say so. Don't force-fit.
- **Latency matters operationally.** A dataset that would work in every other way but arrives 3 weeks late is useless for SAR decisions.

## Variations by Story Type

### Operational Stories (SAR, Volcanic Ash, Rail Heat)
- **Latency is the hardest constraint.** Geostationary + real-time processing required.
- **May require fusion** (satellite + model + ground sensors).
- If earthdata-mcp returns only polar-orbiters, state the gap clearly.

### Retrospective / Scientific Stories (Beavers, Permafrost, Tree Mortality)
- **Latency is permissive** (weeks to months OK).
- **Time span is critical** (10+ year archive needed).
- May trade off resolution for temporal continuity (e.g., MODIS daily is coarser but never cloudy like Landsat).

### Multi-Axis Stories (LA Olympics)
- **Break into sub-needs.** Each hazard (heat / AQI / seismic / fire) is its own constraint set.
- Rank each independently, then synthesize ("Heat needs LST daily; AQI needs Tropomi daily; seismic needs static maps; fire needs MODIS + Landsat trend").

### Scale-Trap Stories (Bridge, Rail, Small Streams)
- **Expect satellite to fail on resolution.**
- Recommend drone / airborne / ground sensors upfront.
- Don't force earthdata-mcp to solve a problem it can't.
